## Steps

1. **Subclass Agent.** Define a Python class that inherits from `nooa.Agent`. If the class has no `...` methods at all, it doesn't need to subclass `Agent`.
2. **Add a generation method.** Give it a body of just `...`. A method with an `...` body is a generation method — implemented at runtime by an LLM-driven strategy. A method with a real body stays deterministic Python.
3. **Write the docstring as the prompt.** The docstring is instructions only, describing what the LLM should do. Do NOT use `{param}` templating for arguments — the framework already renders every parameter to the LLM (via the method signature, CodeAct prefill, and Predict serialization). Reserve `{...}` templating only for things the signature can't show: instance state (`{self.attr}`) or computed expressions (`{len(items)}`).
4. **Add type annotations.** Parameter types and the return type form the contract. Use a Pydantic model (or dataclass, TypedDict, primitive, or container) as the return type to force structured output.
5. **Call the method.** Calling it triggers LLM execution. NOOA validates the output against the return type and auto-retries on validation failure — the LLM sees the validation error message and self-corrects. Callers only ever see well-typed data; there's no separate "did it parse" step.

## Design rules

- **One method = one LLM task.** Don't combine classification + implementation in one generation method — split into separate methods.
- **Renaming changes behavior.** The method name, parameters, and docstring together ARE the prompt — renaming `analyze_feedback` to `analyze_feedback_briefly` changes the output with no other code changes.
- **Orchestrators stay pure Python.** Workflow sequencing methods should have real bodies (no `...`) and call generation methods for each step.
- **Prefer helpers over prompting.** If logic can be deterministic, write it as a regular method rather than asking the LLM to figure it out. Define helpers as class methods (not lambdas/functions assigned to `self`) so they're visible via `doc(self)`.
- **Visibility is opt-out, not opt-in.** Public methods/fields are visible to the LLM by default (via `doc(self)` and execglobals); hide with `@hidden` or `Annotated[T, hidden]`. Private methods/fields are hidden by default; re-expose with `@spec(hidden=False)`.
- **Types must be at module level.** Any type used in the agent's public API (params, return type, fields) must be defined/imported at module level to appear in execglobals — there's no automatic injection.

## Prerequisites

- Python 3.7+
- `nooa` package installed (`pip install nooa` or `uv add nooa`)
- An LLM client configured — quickstart provides `llm`, or import `getllmclient()` from `nooa.unifiedllm` (wraps litellm; any litellm model name works)

## Progressive disclosure

Use `doc(self)` to see the auto-generated API documentation of an agent's visible methods/fields — this is what the LLM sees as its available tools/capabilities.
